How Bob works

Four ideas explain almost everything about working with Bob: who Bob is being (modes), the standards it follows (rules), what it can remember (tasks and context), and what it can reach (MCP). Read through, then play with the interactive parts.

The mental model

Role. Standards. Memory. Reach.

Bob is an AI coding partner that lives in your IDE. It can read your files, edit them, run commands and call tools, but how it does that is shaped by four things you control.

1 · Modes

Same Bob, different job

A mode is a persona plus a set of permissions. Switch modes with the mode selector in the Bob panel. Switching changes what Bob is good at, and just as importantly, what it is not allowed to do.

Use it before building. Design the architecture, break a problem down, write a specification. Great for new projects and complex features.

Try: "Plan a single-file class registration page. What should it show, what checks should it run, and what could go wrong?"

Use it to make changes. Implement features, fix bugs, refactor, and run commands. It has the fullest tool access, which is why it is also the mode to be most careful with.

Name note: the Bob docs call this mode Agent on some pages and Code on others. It is the same job: the mode that writes code.
Try: "Build the plan as registration.html in this folder."

Use it to understand. Explanations, code analysis and recommendations, with no file changes and no commands. Safe to point at an unfamiliar codebase.

Try: "Explain how this project loads its data. Don't change anything."

Bob's docs also list Advanced and Orchestrator as built-in modes, and Bob Shell describes Advanced as the mode for extended capabilities including MCP tools. Check your version's mode list for the full picture.

The pattern that works: Plan → Agent → (Ask whenever you need to understand something). Five minutes planning saves thirty fixing.

Build your own mode

A custom mode combines a role, behavior instructions and a fixed set of permitted tools. The permission list is what makes it trustworthy: a mode without edit in its groups cannot modify files, even if you ask it to.

.bob/custom_modes.yaml
customModes:
  - slug: registrar-reviewer
    name: 🛡️ Registrar Reviewer
    description: Read-only reviewer for privacy and accessibility
    roleDefinition: >-
      You are a skeptical university IT reviewer. You report
      findings; you never modify files.
    whenToUse: Use after building a page, before showing it to anyone.
    customInstructions: |-
      Report PRIVACY, ACCESSIBILITY and DATA HONESTY findings,
      then a verdict. Quote the exact line for every finding.
    groups:
      - read
      - mcp
  • Edit it from Bob: Settings → Modes → Edit Project Modes (project) or the global equivalent.
  • Reuse a built-in slug (for example ask) in your project file to override that built-in mode. Project overrides beat global overrides, which beat defaults.
  • Rules still apply in custom modes. A custom mode adds mode-specific behavior; it does not bypass your rules.

2 · Rules

Say it once. Bob remembers it every time.

Rules are instructions Bob reads at the start of every task, in every conversation. They are for standards that should never need repeating: branding, security expectations, test commands, naming conventions.

    • Files in a rules folder are loaded alphabetically, so numbering them (01-style.md, 02-security.md) controls order.
    • Run /init once in a new project. Bob studies the codebase and writes an AGENTS.md plus a per-mode file for each built-in mode.
    Rules cost context. They are loaded at the start of every task and re-sent with every message. A 3,000-word rules file is a tax you pay on everything. Keep rules short and specific; see the next section.

    3 · Tasks & context

    Every task has a memory, and it fills up

    Each task (one conversation in the Bob panel) has its own context window: the fixed amount of text Bob can hold in mind at once. Everything counts against it: instructions, rules, tool descriptions, your prompts, Bob's replies, every file it reads and every command output.

    Fixed overhead (loaded at the start)

    • System prompt: Bob's core instructions
    • Tool definitions: what Bob can do
    • MCP tools: descriptions of every connected server's tools
    • Rules: your rule files and AGENTS.md
    • Skills: loaded skill instructions

    The docs' small-project example: just saying hi costs about 8.5k tokens before you've done anything. Most of that is tool definitions.

    Grows with every turn

    • Messages: your prompts, Bob's replies, file reads, command output, @ mentions

    In a short chat, fixed overhead dominates. Once Bob reads files and runs tools, Messages becomes the largest slice, and it never shrinks on its own.

    Number check. The Bob docs state the cap as 270,000 tokens on the context-window page and 200,000 in one tutorial; this varies by version. About 20k is typically reserved for Bob's next reply. Look at the token usage indicator in the top right of your Bob panel; hover or click it for the breakdown.

      What to take from the simulator

      • Condensation is lossy. When the window nears its limit, Bob keeps recent and relevant context, summarizes or drops older parts, and keeps system instructions, tool definitions, rules and skills. Notice the early messages that get crossed out: details from early in a long chat may not survive.
      • A new task is a clean slate. Click + (New task) in the Bob panel. Messages start empty again, but your project rules, MCP servers and skills load in again. The old conversation stays in history; it is simply not part of the new window.
      • Cost follows size. Each message re-sends the full active context, including fixed overhead, so long threads get slower and use more Bobcoins per prompt.
      • Long threads can get worse, not just bigger. Abandoned plans, stale file contents and old errors pile up and can steer Bob wrongly (the docs call this context poisoning). Symptoms: repeated suggestions, wrong tool use, fixes that don't stick.

      Habits that keep Bob sharp

      DoWhy
      Start a new task when the goal changesDrops stale messages; fixed overhead reloads automatically
      Point at files with @ instead of "read the whole repo"Targeted context beats broad context
      Keep rules and AGENTS.md shortThey are paid for on every message
      Connect only the MCP servers and skills this work needsEach one adds tool descriptions to the fixed overhead. Prefer project-scoped MCP over global
      Break big jobs into small, reviewable stepsSmaller diffs, fewer wrong turns, easier to undo
      Put constraints you'd repeat into a rule instead of the promptPrompts live in Messages and can be condensed away; rules are preserved

      4 · Connecting to MCP servers

      Give Bob hands outside your repo

      MCP (Model Context Protocol) is an open standard for exposing tools and data to an AI. An MCP server might wrap a database, a ticketing system, a campus data feed, or a docs search. Once connected, Bob can call its tools instead of guessing.

      1. Pick how the server runs (the transport). Local on your machine, or remote over HTTP. See the tabs below.
      2. Open the config. In the Bob panel click the Settings (gear) icon → MCP tab → Edit Project MCP (creates .bob/mcp.json in your project) or Edit Global MCP (~/.bob/mcp.json, all projects).
      3. Add the server under mcpServers, using one of the formats below. Save the file; Bob picks up changes.
      4. Check the MCP tab. The server should show as connected, with its tools listed. If not, see troubleshooting.
      5. Use it. Ask for something only the tool can answer. Bob shows the tool call and its result; open it and read what came back.

      Choose a transport

      Bob starts the server as a child process on your machine. Lowest latency, nothing exposed to the network, simplest setup. Best default for local prototypes.

      .bob/mcp.json
      {
  "mcpServers": {
    "wvu-campus": {
      "command": "node",
      "args": ["${workspaceFolder}/wvu-campus-mcp/build/index.js"],
      "env": { "SOME_SETTING": "value" }
    }
  }
}

      command is required (node, python, npx…). Optional: args, cwd, env, alwaysAllow, disabled. Many published servers run with "command": "npx", "args": ["-y", "<package>"].

      The server runs somewhere else and Bob connects by URL. This is the modern standard for remote servers: it can be shared by many users and centrally managed.

      .bob/mcp.json
      {
  "mcpServers": {
    "campus-data": {
      "type": "streamable-http",
      "url": "https://mcp.example.com/mcp",
      "headers": { "Authorization": "Bearer ${env:CAMPUS_MCP_TOKEN}" }
    }
  }
}

      url is required; headers carries auth. The URL above is a placeholder; use your own server's endpoint.

      The older remote protocol. Still supported, but the docs recommend Streamable HTTP for anything new. You will mostly meet this when connecting to an existing server that only offers SSE.

      .bob/mcp.json
      {
  "mcpServers": {
    "legacy-server": {
      "url": "https://mcp.example.com/sse",
      "headers": { "Authorization": "Bearer ${env:LEGACY_MCP_TOKEN}" }
    }
  }
}
      STDIOStreamable HTTP / SSE
      RunsOn your machine onlyLocal or remote
      UsersOne clientMany clients
      SetupSimpleNeeds an HTTP server

      Project vs. global config

      • Project .bob/mcp.json: lives with the repo, shareable with your team. If the same server name exists in both places, project wins.
      • Global ~/.bob/mcp.json: available in every workspace.
      • Because every connected server adds to your fixed context overhead, prefer project config and only connect what the current work needs. There is also a setting to turn MCP servers off entirely, which removes their instructions from Bob's prompt.

      Staying safe

      MCP tools can read data and take actions. Treat servers like you treat software you install.
      • Connect only servers you trust. The docs rate auto-approving MCP tools as a medium-high risk.
      • Tool auto-approval is off by default. You approve each call, or tick Always allow per tool once you trust it. Don't blanket-approve a server you haven't read.
      • Never put real secrets in a file you commit. Reference environment variables instead, like ${env:NAME} in the examples (and ${workspaceFolder} for paths). Check your Bob version supports this before relying on it.
      • For this event: no real student data goes through any server. Use the simulated data provided.

      Troubleshooting

      SymptomTry
      Server not listed, or shows an errorCheck the JSON is valid (a missing comma is the usual culprit). Confirm the command exists on your PATH (node -v).
      STDIO server won't startRun the exact command + args in a terminal. Use absolute paths if ${workspaceFolder} isn't expanding in your version. For servers you write, log to stderr, never stdout: stdout is the protocol channel.
      Connected, but Bob never uses the toolsMake sure you are in a mode that has MCP access, and that MCP servers are enabled in settings. Ask directly: "use the <server> tool to…".
      Remote server returns 401/403Check the header, and that the environment variable is set in the same environment Bob was launched from. Restart Bob after changing it.
      Bob feels slow or forgetful after adding serversOpen the context breakdown. Large MCP Tools means too many servers or tools; disable what you aren't using.
      In the lab you'll connect a small local STDIO server of simulated WVU course, travel-time and study-room data, then ask Bob questions only its tools can answer. Want to write your own server? Ask Bob: "Build me an MCP server that exposes …"; it can scaffold, build and register one for you.
