How Bob works

Three ideas explain almost everything about working with Bob: who Bob is being (modes), the reusable instructions it loads (skills), the standards it follows (rules), and what it can remember (tasks and context). Then two more: how you stay in control (approvals) and how Bob documents its work (docs). Read through, then play with the interactive parts.

The mental model

Role. Standards. Memory.

Bob is an AI coding partner that lives in your IDE. It can read your files, edit them, run commands and call tools, but how it does that is shaped by six things you control.

1 · Rules

Say it once. Bob remembers it every time.

Rules are instructions Bob reads at the start of every task, in every conversation. They are for standards that should never need repeating: branding, security expectations, test commands, naming conventions.

See the difference

    # WVU house rules
- Primary color #002855, accent #EAAA00
- Single HTML file, no network requests
- Label every data source LIVE or SIMULATED
- Show a "Simulated data" badge
- Explain how student data is protected
- Keyboard-accessible, labeled inputs

    Where rules live

    LocationApplies toGood for
    .bob/rules/This project, every modeTeam standards you can commit to the repo
    .bob/rules-{mode-slug}/This project, one mode onlye.g. testing rules just for the coding mode, architecture rules just for Plan
    ~/.bob/rules/Every project on your machineYour personal preferences
    AGENTS.mdThis projectProject overview, build and test commands. Generated for you by /init
    • Files in a rules folder are loaded alphabetically, so numbering them (01-style.md, 02-security.md) controls order.
    • Run /init once in a new project. Bob studies the codebase and writes an AGENTS.md plus a per-mode file for each built-in mode.
    Rules cost context. They are loaded at the start of every task and re-sent with every message. A 3,000-word rules file is a tax you pay on everything. Keep rules short and specific; see the next section.

    2 · Skills

    Deep expertise, loaded on demand

    A skill is a reusable instruction set — a SKILL.md file — that gives Bob focused, domain-specific know-how for a particular task. Unlike rules (which are always on), a skill is activated deliberately at the start of the work that needs it, then it stays loaded for that task only.

    Why skills exist

    Some work requires detailed, expert-level instructions that are too long to repeat in a prompt and too specialized to add to every-session rules. Examples: a Carbon Design System component guide, a watsonx deployment checklist, a company-specific API integration pattern. A skill packages that expertise once; you — or Bob — activate it when needed.

    Skills vs. rules. Rules are always loaded, every task, and cost context every time. A skill is opt-in: it only uses context in tasks where you've activated it. Use rules for universal standards; use skills for specialized, task-specific expertise.

    Where skills live

    LocationApplies toGood for
    .bob/skills/This projectProject-specific know-how shared with your team
    ~/.bob/skills/Every project on your machineYour personal expert instruction sets

    Each skill lives in its own subfolder with a SKILL.md file. The subfolder name becomes the skill's name.

    Anatomy of a skill

    .bob/skills/wvu-registration/SKILL.md
    ---
name: wvu-registration
description: >-
  WVU course registration patterns — component names, data
  sources, accessibility requirements, and simulated-data rules.
  Use when building or reviewing any registration page.
---

# WVU Registration — Expert Guide

## Component conventions
- Use WVU Blue (#002855) as the primary color, Old Gold (#EAAA00) as accent.
- All data tables must include a caption and a "SIMULATED DATA" badge.

## Accessibility requirements
- Every form input must have an explicit <label>.
- Color must not be the only way information is conveyed.

## Data rules
- Never fetch live student data; use the provided simulated JSON files.
- Always display a "Simulated data — not real student records" notice.

    How to activate a skill

    Bob can activate a skill automatically when the task matches its description, or you can activate it yourself:

    • Ask Bob directly: "Activate the wvu-registration skill, then build the page." Bob reads the SKILL.md into its context for this task.
    • Bob auto-activates: When Bob recognises the task matches a skill's description, it may propose activating it. Activating a skill is a Skill-category action — Bob asks for approval before loading it (unless you've auto-approved that category).
    • From the marketplace: Skills can be installed from the Bob Marketplace (the shopping-bag icon in the Bob panel). Installed marketplace skills are then available to activate like any local skill.
    Skills cost context too. A skill's instructions are added to the fixed overhead for the task it's loaded in. Keep skill files focused — expert depth on a single topic is more useful (and cheaper) than a broad catch-all guide.

    Build a skill for your project

    Here's a starter prompt that asks Bob to write a skill for your project:

    Prompt
    Create .bob/skills/wvu-registration/SKILL.md.
The skill should capture the design, data, and accessibility standards
for our WVU registration page so any future task starts with them
already loaded. Include: color palette, form/table rules, simulated-data
disclaimer wording, and the ARIA patterns we used.
    • Once created, test it by starting a new task and asking: "Activate the wvu-registration skill, then review our registration page for accessibility issues."
    • Skills are plain Markdown — edit them like any other file when requirements change.

    3 · Modes

    Same Bob, different job

    A mode is a persona plus a set of permissions. Switch modes with the mode selector in the Bob panel. Switching changes what Bob is good at, and just as importantly, what it is not allowed to do.

    Use it before building. Design the architecture, break a problem down, write a specification. Great for new projects and complex features.

    Try: "Plan a single-file class registration page. What should it show, what checks should it run, and what could go wrong?"

    Use it to make changes. Implement features, fix bugs, refactor, and run commands. It has the fullest tool access, which is why it is also the mode to be most careful with.

    Name note: the Bob docs call this mode Agent on some pages and Code on others. It is the same job: the mode that writes code.
    Try: "Build the plan as registration.html in this folder."

    Use it to understand. Explanations, code analysis and recommendations, with no file changes and no commands. Safe to point at an unfamiliar codebase.

    Try: "Explain how this project loads its data. Don't change anything."

    Bob's docs also list Advanced and Orchestrator as built-in modes. Check your version's mode list for the full picture.

    The pattern that works: Plan → Agent → (Ask whenever you need to understand something). Five minutes planning saves thirty fixing.

    Build your own mode

    A custom mode combines a role, behavior instructions and a fixed set of permitted tools. The permission list is what makes it trustworthy: a mode without edit in its groups cannot modify files, even if you ask it to.

    .bob/custom_modes.yaml
    customModes:
  - slug: registrar-reviewer
    name: 🛡️ Registrar Reviewer
    description: Read-only reviewer for privacy and accessibility
    roleDefinition: >-
      You are a skeptical university IT reviewer. You report
      findings; you never modify files.
    whenToUse: Use after building a page, before showing it to anyone.
    customInstructions: |-
      Report PRIVACY, ACCESSIBILITY and DATA HONESTY findings,
      then a verdict. Quote the exact line for every finding.
    groups:
      - read
    • Edit it from Bob: Settings → Modes → Edit Project Modes (project) or the global equivalent.
    • Reuse a built-in slug (for example ask) in your project file to override that built-in mode. Project overrides beat global overrides, which beat defaults.
    • Rules still apply in custom modes. A custom mode adds mode-specific behavior; it does not bypass your rules.

    4 · Tasks & context

    Every task has a memory, and it fills up

    Each task (one conversation in the Bob panel) has its own context window: the fixed amount of text Bob can hold in mind at once. Everything counts against it: instructions, rules, tool descriptions, your prompts, Bob's replies, every file it reads and every command output.

    Fixed overhead (loaded at the start)

    • System prompt: Bob's core instructions
    • Tool definitions: what Bob can do
    • Rules: your rule files and AGENTS.md
    • Skills: loaded skill instructions

    The docs' small-project example: just saying hi costs about 8.5k tokens before you've done anything. Most of that is tool definitions.

    Grows with every turn

    • Messages: your prompts, Bob's replies, file reads, command output, @ mentions

    In a short chat, fixed overhead dominates. Once Bob reads files and runs tools, Messages becomes the largest slice, and it never shrinks on its own.

    Number check. The Bob docs state the cap as 270,000 tokens on the context-window page and 200,000 in one tutorial; this varies by version. About 20k is typically reserved for Bob's next reply. Look at the token usage indicator in the top right of your Bob panel; hover or click it for the breakdown.

      What to take from the simulator

      • Condensation is lossy. When the window nears its limit, Bob keeps recent and relevant context, summarizes or drops older parts, and keeps system instructions, tool definitions, rules and skills. Notice the early messages that get crossed out: details from early in a long chat may not survive.
      • A new task is a clean slate. Click + (New task) in the Bob panel. Messages start empty again, but your project rules and skills load in again. The old conversation stays in history; it is simply not part of the new window.
      • Cost follows size. Each message re-sends the full active context, including fixed overhead, so long threads get slower and use more Bobcoins per prompt.
      • Long threads can get worse, not just bigger. Abandoned plans, stale file contents and old errors pile up and can steer Bob wrongly (the docs call this context poisoning). Symptoms: repeated suggestions, wrong tool use, fixes that don't stick.

      Habits that keep Bob sharp

      DoWhy
      Start a new task when the goal changesDrops stale messages; fixed overhead reloads automatically
      Point at files with @ instead of "read the whole repo"Targeted context beats broad context
      Keep rules and AGENTS.md shortThey are paid for on every message
      Load only the skills this work needsEach loaded skill adds instructions to the fixed overhead. Keep skills focused and modular
      Break big jobs into small, reviewable stepsSmaller diffs, fewer wrong turns, easier to undo
      Put constraints you'd repeat into a rule instead of the promptPrompts live in Messages and can be condensed away; rules are preserved

      5 · You stay in control

      Bob asks before it acts

      Bob doesn't silently change your project. Before it edits a file or runs a command, an approval prompt appears and waits for you. You decide how many of those prompts you want to see, per type of action.

      What a prompt looks like and what you can do with it

      • One at a time. Prompts appear individually so each action gets a clear, deliberate look before it runs.
      • Previews, not walls of text. Large details like a full file diff or long command output are collapsed into a preview; expand it if you want everything.
      • Edit before you approve. When Bob proposes a terminal command, you can change the command right in the prompt instead of rejecting and re-explaining.
      • Reject any time. Say no, then tell Bob what to do differently.
      • Per-task overrides. You can set approvals for the current task only, independent of your global settings.

      What happened

        Try these three experiments

        1. Manual. Approve everything, but on the command prompt change open registration.html to something else before approving. That's the editable-command feature.
        2. Hybrid. Only the low-risk bookkeeping (to-do list, subtasks, subagents, mode switches) goes through silently. The prompts that matter still reach you.
        3. Everything. Nothing interrupts you, including the edit and the command. Read the summary at the end.

        Not all actions are equally risky

        ActionWhat it allowsRisk (per docs)
        ReadView files and foldersMedium consider sensitive data exposure
        EditCreate, edit and save filesHigh enable only in controlled environments
        ExecuteRun terminal commandsHigh use an allow-list of trusted commands; avoid wildcards
        SkillActivate skillsMedium Bob asks before activating a skill by default
        Todo, Subtask, Subagent, ModeTask management and switching modesLow
        Why this matters. The docs warn that auto-approval bypasses confirmation prompts and can lead to data loss or file corruption; command execution is the most dangerous. Start restrictive, add permissions only as you need them, use different settings per project, and never auto-approve in production.

        Guardrails beyond the popup

        Mode permissions

        Limit what a mode can do

        A mode without edit or command in its groups can't change files or run commands at all. See the Registrar Reviewer in the Modes section.

        .bobignore

        Fence off files

        List files Bob must not access or modify, using .gitignore syntax. Good for secrets, credentials and generated output.

        Rollback

        Undo a bad turn

        Hover over a prompt in the chat and click Rollback to restore your files to that point. Docs tip: faster than correcting flawed output with more instructions.

        .bobignore

        Human in the loop also means Bob asks you. When a request is ambiguous, Bob can stop and ask clarifying questions, often with options to click, before it builds. Plan mode does this a lot. Answer them; it's cheaper than fixing a wrong guess.
        Reviews run differently. The docs note that the /review code-review workflow runs with auto-approval through its analysis steps. It reports findings; check what you've enabled before you start it.

        6 · Documentation on demand

        Bob writes the docs, too

        Code that nobody can explain is a liability. Bob can read your project and write documentation as real files in your workspace: Markdown for repos and wikis, HTML for anything you want to hand to a non-developer. This is the part that makes a prototype something an IT team can actually evaluate.

        A README that matches the code, not what the code looked like last month.

        Prompt
        Write a README.md for this project based on @src/app.js.
Include: what it does, how to install and run it, the features it provides,
and a clear note that all data is simulated.

        Use @ to point Bob at the exact files to document, so it reads what matters instead of exploring the whole repo (and spending your context).

        Plan mode already writes .md plan files when you ask. The same works for design documentation after the fact.

        Prompt
        Create docs/ARCHITECTURE.md describing how the registration page, the
feasibility engine, and the data files fit together. Include a Mermaid diagram,
a table of data sources marked LIVE or SIMULATED, and a "path to
production" section listing what WVU IT would need to provide.

        Mermaid diagrams in Markdown render on GitHub and many wikis, so the diagram travels with the repo.

        Not everyone reads Markdown. Ask for a single self-contained HTML file and you get something you can email, open by double-click, or present from.

        Prompt
        Create guide.html: a single self-contained page (inline CSS and JS, no
external requests) that explains this project to a non-technical reader.
Use the style in templates/client_page_template.html. Include a short
walkthrough with screenshots-as-text, and a FAQ.
        You're looking at one. This walkthrough, the reference page, and the architecture guide were all drafted with Bob from prompts like the ones above, then reviewed by a person.

        Documentation can live in the code itself.

        Prompt
        Add JSDoc comments to every function in @src/helpers.js.
Don't change any logic.

        Pair with the approval prompt: because "don't change any logic" is a claim, check the diff Bob shows you before approving the edit.

        Make it repeatable

        A docs-only mode

        Give Bob a technical-writer persona that can only edit Markdown files. It can read your whole project but cannot touch code, so documentation work is low-risk by construction. (This mirrors an example in the Bob docs.)

        customModes:
  - slug: docs-writer
    name: 📝 Documentation Writer
    description: Writes and revises Markdown docs
    roleDefinition: You are a technical writer.
    whenToUse: Use for writing and editing docs.
    customInstructions: |-
      Be clear and accurate.
      Never invent behavior; say "unknown" when unsure.
    groups:
      - read
      - - edit
        - fileRegex: ".*\\.(md|mdx)$"
          description: Markdown files only

        A rule that keeps docs honest

        Put your documentation standards in a rules file so every README and guide follows them without being asked.

        # Documentation rules
- Every project gets a README with:
  what it is, how to run it, how to test it.
- Label every data source LIVE or SIMULATED.
- State what is NOT verified or not built.
- Examples use fictional names and @example.com.
- Never document behavior you haven't read
  in the code.
        Documentation is a draft until a person checks it. Bob writes quickly and fluently, which makes errors easy to miss. Check commands actually run, file paths exist, and nothing claims a feature the code doesn't have. Rules like "don't document behavior you haven't read" help, but the review is yours. This is the approval-prompt idea applied to docs.
